## Where things stand (one paragraph)

Real-audio mode is **functionally done in source**: `tools/hat-sound.c`
plays raw s16le 48 kHz mono through the proven 192 kHz / OS=4
sigma-delta tick clock, feeds via a ring, drains at EOF, parks the amp pin
LOW, and exits 0. A dedicated bench that compiles the **exact engine
source** proves the consumer runs at exactly 1 sample / 4 ticks (correct
48 kHz). **BUT** every on-board run reports the whole 264 000-sample file
consumed in only ~264 000 ticks (~1.4 s) instead of ~1 056 000 ticks
(~5.5 s) — i.e. the field behaves like **1 sample / tick (4× rate)** even
though the source is provably 4 ticks/sample. The pacing mismatch between
the proven-correct source and the observed field is the single open bug.
A self-report line was added to `hat-sound` so the next on-board run
self-rates itself; **that run has not yet been executed by the operator.**

## What "done" looks like (definition of done)

Real audio is DONE when a on-board `sudo /home/cj/hat-sound -F

`... consumed 528000 B (264000 samples, 48000.0 Hz, 1.00x real-time)

## The debugging saga (what I tried / what worked / what didn't)

### Bug v1 — segfault, exit 139 (RUN 1, 01:42 binary)
`feed_more()` passed a `free_n` of up to 8190 bytes to `read()` at the
wrapped offset `g_prod & g_mask`; when `at` was near 8190 the write ran
past the 8 KB `malloc` (heap smash) ~10 ms in.
**Fix:** cap each read at `tail = RING_MAX - at` so a full ring fills
across two reads and nothing ever straddles the buffer end. Collateral:
odd-`read()`-byte tolerance in `sample_next` (`g_cons + 2 <= g_prod`) +
EOF-drain guard (`g_cons + 2 > g_prod`); `feed_thread` no longer treats
`-10` (ring full) as EOF (stdin pipe truncation). Rebuilt 01:44,
(RUN 2) exit 0.

### Bug v2 — post-EOF feed spam (RUN 3, 01:45 binary)
After EOF the engine feed gate kept calling `feed_more()` every tick
during ring drain → re-hit EOF, re-print `EOF after 528000 source bytes`
350×, and `fprintf` stole CPU from the 5.2 µs tick → sputtered tail.
**Fix:** `!g_feed_eof` guard on the gate. Applied to source (the run that
used it printed a clean single EOF line → **this fix is confirmed
working**).

### Open bug v3 — the 4× pacing / 1.4 s anomaly (RUN 2, RUN 4, RUN 5)
SYMPTOM: stats show `t=1.4s ticks≈264000-265000` for a 5.5 s / 1 056 000-
tick file, `und≈1`, `duty≈49-50%`, `x1ms=0 x10ms=0` (clean clock). The
whole 528 000-byte file IS consumed (self-report will confirm `consumed
528000`); it just happens in ~264 000 ticks instead of ~1 056 000.
**Interpretation:** 264 000 samples / 264 000 ticks ≈ 1 sample per tick
= 4× the intended 48 kHz ⇒ audio played ~4× fast (440 Hz heard as ~1760
Hz). The clock is NOT the cause (dev is tens of ns, x10ms=0).

   4 ticks/sample. No smoking gun in the source.
