## Where things stand (one paragraph)

Real-audio mode is **done in source**: `tools/hat-sound.c` plays raw
s16le 48 kHz mono through the proven 192 kHz / OS=4 sigma-delta tick
clock, feeds via a ring, drains at EOF, parks the amp pin LOW, and exits
0. **The 4× pacing bug is ROOT-CAUSED and fixed (v3.4)**: the 4-tick
overrun re-anchor at the bottom of `main()`'s loop compared
`now - next` UNSIGNED; on a healthy clock `now < next`, so the
difference underflows to ~2^64 and the test was true EVERY tick —
resetting `tis` to 0 every tick. Mode 0 then advanced its sine phase
every tick (all sigma tones ~4× pitch — the long-unexplained "modem"
character of early runs) and mode 2 consumed a ring sample EVERY tick
(4× real-time; the self-report run measured **3.98×**). A bench that
links the real engine looked correct because it never ran `main()` —
the engine alone was always 1 sample / 4 ticks; only the loop around it
was broken. `-p` mode was immune (elapsed-time math only), which is why
the square wave always sounded right. Fix: signed compare
`(int64_t)(now - next) > (int64_t)(4*TICK_NS)`. The v3.4 binary is
built (10:14, md5 `38281b372cb30c292a02efb3e0e59a5f`); **one operator
run of `sudo /home/cj/hat-sound -F /home/cj/test.s16` closes it** —
expect `1.00x real-time`, 4 tones at normal pitch, ~5.5 s.

## The debugging saga (what I tried / what worked / what didn't)

### Bug v1 — segfault, exit 139 (RUN 1, 01:42 binary)
`feed_more()` passed a `free_n` of up to 8190 bytes to `read()` at the
wrapped offset `g_prod & g_mask`; when `at` was near 8190 the write ran
past the 8 KB `malloc` (heap smash) ~10 ms in.
**Fix:** cap each read at `tail = RING_MAX - at` so a full ring fills
across two reads and nothing ever straddles the buffer end. Collateral:
odd-`read()`-byte tolerance in `sample_next` (`g_cons + 2 <= g_prod`) +
EOF-drain guard (`g_cons + 2 > g_prod`); `feed_thread` no longer treats
`-10` (ring full) as EOF (stdin pipe truncation). Rebuilt 01:44,
(RUN 2) exit 0.

### Bug v2 — post-EOF feed spam (RUN 3, 01:45 binary)
After EOF the engine feed gate kept calling `feed_more()` every tick
during ring drain → re-hit EOF, re-print `EOF after 528000 source bytes`
350×, and `fprintf` stole CPU from the 5.2 µs tick → sputtered tail.
**Fix:** `!g_feed_eof` guard on the gate. Applied to source (the run that
used it printed a clean single EOF line → **this fix is confirmed
working**).

### Bug v3 — the 4× pacing / 1.4 s anomaly — ROOT-CAUSED, FIXED v3.4
SYMPTOM: stats show `t=1.4s ticks≈264000-265000` for a 5.5 s / 1 056 000-
tick file, `und≈1`, `duty≈49-50%`, `x1ms=0 x10ms=0` (clean clock). The
whole 528 000-byte file IS consumed (self-report confirmed `consumed
528000 B (264000 samples, 191051.2 Hz, 3.98x real-time)`, operator's
screen, 10:10 run); it just happens in ~264 000 ticks instead of
~1 056 000. **Interpretation:** 264 000 samples / 264 000 ticks ≈ 1
sample per tick = 4× the intended 48 kHz ⇒ audio played ~4× fast (440
Hz heard as ~1760 Hz). The clock is NOT the cause (dev is tens of ns,
x10ms=0) — confirmed: 1.38 s × 192 kHz ≈ 264k ticks exactly.

**ROOT CAUSE (found by reading `main()`'s loop, which the bench never
exercised):** the 4-tick overrun re-anchor
```
if (now - next > 4 * TICK_NS) { next = now + TICK_NS; tis = 0; }
```
uses `uint64_t` operands. After `wait_deadline` on a HEALTHY clock
`now < next` (deadline still ahead) ⇒ `now - next` wraps to ~2^64 ⇒
comparison true EVERY tick ⇒ `tis` forced to 0 every tick. Since the
element's pacing key is `if (*tis == 0) sample_next()` (and mode 0's
phase advance), consumption/phase ran at one-per-tick instead of
one-per-4-ticks. It is invisible to: the engine bench (engine called
directly, no loop), the clock stats (re-anchoring a clean clock adds no
deviation — that's why x10ms=0 stayed clean), and `-p` (uses elapsed
time only). Also retro-explains: all sigma-delta tones in v3 runs being
~4× pitch ("modem"), and the "byte-identical stats across runs" being
DETERMINISTIC re-execution of the bug, not file staleness (that lesson
holds, but the real explanation was this).

**FIX (v3.4):** `if ((int64_t)(now - next) > (int64_t)(4 * TICK_NS))` —
signed; true condition now means genuinely behind by >4 ticks.
Documented in the code comment + file header. Rebuilt 10:14, zero
warnings, md5 `38281b372cb30c292a02efb3e0e59a5f` (73 520 B). Bench
re-run: still `consumed = t/2`, exit 0 (engine untouched). **Awaiting
one operator live run: expect `1.00x real-time`.**
